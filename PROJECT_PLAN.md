# Smart Study Assistant Bot — Build Plan

This is the implementation spec for the final-year project documented in
`Hafiz project\Smart Study Assistant Bot - Chapters 1-3.docx` (Chapters 1–3: Introduction,
Literature Review, Methodology). Every functional/non-functional requirement, the architecture,
and the database schema below are taken directly from Chapter 3 so the built app matches what was
submitted. Give this whole file to Claude Code in this folder and build it phase by phase.

## 1. What this is

A web-based conversational AI study assistant, piloted on four courses at Federal University
Dutse: **CSC311 (Data Structures)**, **CSC313 (Operating Systems)**, **CSE301 (Software Design and
Architecture)**, **CSE304 (Web Application Development)**. Students ask questions grounded in
curated course material (RAG — no ungrounded answers); lecturers upload material and see an
anonymized dashboard of which topics students are struggling with, generated by a second periodic
LLM prompt (not a trained ML classifier — that idea was explicitly rejected, don't reintroduce it).

## 2. Tech stack (locked)

| Layer | Choice |
|---|---|
| Frontend | Next.js (TypeScript, App Router), Tailwind CSS |
| Backend | FastAPI (Python) |
| Database | PostgreSQL + `pgvector` extension (one relational store, embeddings included — not a separate vector DB) |
| Chat/generation LLM | **Groq**, OpenAI-compatible client, model `openai/gpt-oss-120b` |
| Embeddings | **OpenAI**, model `text-embedding-3-small` (1536-dim), paid via existing OpenAI credit — cheap enough ($0.02/1M tokens) that the pilot corpus barely dents it |
| Auth | JWT, role-based (`student` / `lecturer`), 30-minute inactivity timeout |
| Database hosting | **Supabase** Postgres (free tier) with the `pgvector` extension enabled — one hosted instance used for both local dev and the pilot, no local Postgres/Docker to run |
| Migrations | Alembic |
| Frontend hosting | **Vercel** (free tier) — native fit for Next.js |
| Backend hosting | **Render** free web service tier — runs FastAPI with unrestricted outbound HTTP (needed to call Groq/OpenAI) |
| Scheduler (topic-tagging job) | **External free cron** (a GitHub Actions scheduled workflow, or cron-job.org) calling a protected backend endpoint — see Section 11 and the note below |

No Docker and no local database anywhere in this plan — Supabase is used for local dev too, so
`docker-compose` is unnecessary. Every piece of infrastructure above is free at pilot scale
*except* the OpenAI embeddings API (Section 2, paid from your existing credit — the one deliberate
exception). Two caveats worth knowing going in:
- **Render's free tier spins the backend down after ~15 minutes of inactivity**; the first request
  after a sleep takes 30–50 seconds to cold-start. This can violate the 8-second response NFR
  (Section 7) on that first request only — acceptable for a student pilot, but worth mentioning in
  your evaluation write-up as a known limitation of free-tier hosting rather than a design flaw.
  A cold FastAPI process is also why an in-process scheduler (e.g. APScheduler) can't be relied on
  for the topic-tagging job — it wouldn't fire while the service is asleep, hence the external-cron
  approach above.
- **Groq's API** currently has a free developer tier (rate-limited) — confirm current limits at
  console.groq.com before the pilot; if pilot traffic ever exceeds the free rate limit, that's the
  only other place a cost could appear.

Groq client setup (already decided by the user):
```python
from openai import AsyncOpenAI
import os

client = AsyncOpenAI(
    api_key=os.getenv("GROQ_API_KEY"),
    base_url="https://api.groq.com/openai/v1",
)
MODEL = "openai/gpt-oss-120b"
```
Use this same client for both the conversational engine (Section 8) and the topic-tagging prompt
(Section 9) — one client, one API key, two different system prompts.

Embeddings:
```python
from openai import AsyncOpenAI
import os

openai_client = AsyncOpenAI(api_key=os.getenv("OPENAI_API_KEY"))
EMBED_MODEL = "text-embedding-3-small"  # 1536-dim vectors

resp = await openai_client.embeddings.create(model=EMBED_MODEL, input=text)
vector = resp.data[0].embedding
```
Store vectors in a pgvector `vector(1536)` column. If retrieval quality is unsatisfactory during
testing, `text-embedding-3-large` (3072-dim) is the drop-in upgrade — still cheap at pilot scale,
just change the column dimension and re-embed.

`DATABASE_URL` comes from the Supabase project dashboard (Settings → Database). Use the
**pooler** connection string (port 6543) rather than the direct one (port 5432) — it avoids
IPv6 connectivity issues on networks/hosts that don't support it. `sslmode=require` is mandatory
for Supabase. Before running migrations, enable the extension once via the Supabase SQL editor:
```sql
create extension if not exists vector;
```

## 5. User roles

- **Student**: registers, logs in, selects a pilot course, asks questions, takes self-assessment
  quizzes, views own history and results, can delete own conversation history.
- **Lecturer**: logs in, uploads course material for their pilot course, views the anonymized
  topic-tag dashboard. Never sees individual student identities or raw conversation content.

## 6. Functional requirements (verbatim from Chapter 3 — build to these exactly)

**User Registration and Authentication**
- FR1.1 Registration form: full name, institutional email, department, password.
- FR1.2 Login required before accessing any function.
- FR1.3 Role = Student or Lecturer; lecturer-only functions restricted accordingly.
- FR1.4 Auto-terminate a session idle >30 minutes; require re-login.

**Course Selection and Knowledge Base Access**
- FR2.1 Show pilot courses available for selection to a logged-in student.
- FR2.2 Restrict a student's conversation to the curated knowledge base of the selected course.
- FR2.3 Authorized lecturer can upload course outlines, lecture notes, past-question material.
- FR2.4 Uploaded material is automatically chunked and embedded, retrievable within a defined
  processing window.

**Conversational Question Answering**
- FR3.1 Accept free-text question, retrieve most relevant chunks via semantic similarity search.
- FR3.2 Generate a response using retrieved chunks as grounding context.
- FR3.3 Decline explicitly when no chunk meets the minimum similarity threshold.
- FR3.4 Persist every question/answer exchange (including declines) in conversation history.

**Self-Assessment**
- FR4.1 Student can request a short quiz on a specific topic within the selected course.
- FR4.2 Quiz questions generated from the course's curated knowledge base for that topic.
- FR4.3 Score a completed attempt, store against student profile + topic.
- FR4.4 Student can view their own historical results on request.

**Topic-Tagging and Lecturer Dashboard**
- FR5.1 Periodically aggregate pseudonymized conversation + self-assessment data per pilot course.
- FR5.2 Prompt the LLM, via a structured system prompt, to summarize topics generating the most
  questions or weakest self-assessment results per course.
- FR5.3 Store the generated topic-tag output against the course and the time period covered.
- FR5.4 Display aggregated, anonymized topic-tag output to the pilot lecturer via a dashboard.
- FR5.5 Never show any individual student's identifiable conversation content to a lecturer.

**Data Handling**
- FR6.1 Pseudonymize student identifiers before including interaction data in a topic-tagging prompt.
- FR6.2 Record timestamp, source course, and outcome (answered/declined) of every exchange.
- FR6.3 Student can request deletion of their own conversation history.

## 7. Non-functional requirements (build/test against these)

- **Performance**: grounded response within **8 seconds** under expected pilot load (retrieval +
  LLM API latency).
- **Usability**: chat interface usable with zero AI-tool experience, no manual required.
- **Reliability**: target **95% uptime** during the pilot (single-institution scale, not production HA).
- **Security**: all access authenticated; lecturer functions role-restricted; student data
  pseudonymized in line with the Nigeria Data Protection Act 2023 (NDPA).
- **Scalability**: adding a pilot course = curate + embed its material only, no change to
  retrieval/generation/topic-tagging logic.
- **Maintainability**: retrieval, generation, and topic-tagging kept as distinct, independently
  testable modules/services — don't collapse them into one giant handler.

## 8. System architecture

Three-tier: Next.js (presentation, on Vercel) → FastAPI (application, on Render: auth, RAG
orchestration, topic-tagging endpoint, all API routing) → Supabase PostgreSQL+pgvector (data:
users, courses, conversations, document chunks + embeddings, topic tags). FastAPI calls the
external Groq API for generation and the OpenAI API for embeddings (Section 2).

## 9. Database schema

Relational model, one Postgres database, embeddings via `pgvector`. Entities and fields (from the
Chapter 3 ER diagram):

```sql
User            (user_id PK, name, email UNIQUE, password_hash, role ENUM('student','lecturer'), department, created_at)
Course          (course_id PK, code UNIQUE, title)
Conversation    (conversation_id PK, user_id FK, course_id FK, started_at)
Message         (message_id PK, conversation_id FK, sender ENUM('user','assistant'), content, grounded BOOLEAN, created_at)
KnowledgeDocument (document_id PK, course_id FK, title, source_type, uploaded_by FK->User, created_at)
DocumentChunk   (chunk_id PK, document_id FK, content, embedding VECTOR(1536), created_at)
QuizAttempt     (attempt_id PK, user_id FK, course_id FK, topic, score, attempted_at)
TopicTag        (tag_id PK, course_id FK, topic_label, question_count, period_start, period_end)
```

Course is the relational hub (Conversation, KnowledgeDocument, QuizAttempt, TopicTag all reference
it). Seed the four pilot courses (Section 1) on first migration.

## 10. RAG pipeline design

1. **Ingestion** (FR2.3/FR2.4): lecturer uploads a document → split into passage-level chunks →
   embed each chunk via the OpenAI embeddings API (`text-embedding-3-small`) → store in `DocumentChunk`.
2. **Query time** (FR3.1–FR3.3): embed the student's question with the same model → cosine
   similarity search in pgvector, top-k chunks, scoped to the selected course only (FR2.2) →
   compare best match against a **minimum similarity threshold** (tune empirically during testing;
   start around 0.7–0.75 cosine on this embedding model and adjust from real pilot questions).
   - Below threshold → return an explicit decline message (FR3.3), log as declined (FR6.2).
   - Above threshold → pass retrieved chunks as grounding context to Groq for generation (FR3.2).
3. **System prompt for the conversational engine**: instruct the model to answer strictly from the
   supplied chunks, never introduce outside information, and explicitly say it cannot answer when
   the chunks don't address the question. This is the grounding behavior — don't let the model
   "fill in" from its own general knowledge even when it plausibly could.
4. Persist every exchange (question, answer, grounded flag) to `Message` (FR3.4, FR6.2).

## 11. Topic-tagging pipeline design

Separate, periodic process, not triggered by student action. Since the backend sleeps when idle on
Render's free tier (Section 2), the trigger comes from *outside* the FastAPI process rather than an
in-process scheduler:
1. A `POST /internal/topic-tagging/run` endpoint (protected by a shared secret header, not open to
   the public) performs the aggregation-and-tagging work described below for every pilot course.
2. A free external cron — a GitHub Actions workflow on a `schedule:` trigger (e.g. weekly), or
   cron-job.org hitting the same URL — calls that endpoint on the defined period. The HTTP call
   itself wakes a sleeping Render instance, so this doubles as the wake-up mechanism.
3. Inside that endpoint: aggregate a batch of pseudonymized conversation + quiz-attempt records per
   course over the period — pseudonymize the student identifier before it ever enters the prompt
   (FR6.1). Never include raw message content that could re-identify a student beyond what's needed
   to name a topic.
4. Send a structured system prompt to Groq instructing it to return **fixed-format JSON**: topics
   generating the most questions or weakest self-assessment results, occurrence counts, and
   pseudonymized learner identifiers per topic.
5. Store the parsed JSON in `TopicTag` against `course_id` + period.
6. Lecturer dashboard reads only `TopicTag` rows — never raw `Message`/`Conversation` rows — which
   structurally enforces FR5.5 (no individual identifiable content reaches the lecturer view).

## 14. Suggested build order

Work through these roughly in order — each is independently testable, matching the
maintainability NFR:

1. **Scaffold**: repo structure above, Supabase project created with `pgvector` extension enabled, Vercel project (frontend) and Render web service (backend) created, `.env.example`, health-check route.
2. **Database**: SQLAlchemy models for all 8 entities, Alembic migration, seed the 4 pilot courses.
3. **Auth**: register/login, JWT issuance, role check middleware, 30-min idle timeout (FR1.1–FR1.4).
4. **Ingestion**: document upload endpoint, chunking, OpenAI embedding, storage (FR2.3–FR2.4).
5. **RAG chat**: ask-question endpoint + threshold/decline logic + Groq generation + chat UI (FR3.x).
6. **Self-assessment**: quiz generation from course chunks, scoring, results view (FR4.x).
7. **Topic-tagging**: protected `/internal/topic-tagging/run` endpoint + external cron trigger, Groq structured-JSON prompt, dashboard UI (FR5.x, FR6.1).
8. **History & data handling**: conversation history view, delete-my-history endpoint (FR6.2–FR6.3).
9. **Non-functional pass**: latency check against the 8s target, basic error handling, a handful of
   backend tests per module (retrieval, generation, topic-tagging kept separately testable per the
   maintainability NFR).

## 15. Things to decide as you go (not locked, use judgment or ask)

- Exact chunk size/overlap and top-k for retrieval — tune from real course material during testing.
- Exact similarity threshold value — tune from real pilot questions, don't hardcode a guess as final.
- Quiz question format (MCQ vs short-answer) — MCQ is simplest to auto-score and is a reasonable
  default; short-answer would need LLM-graded scoring, more complex.
- Whether the topic-tagging period is weekly or another cadence — weekly is a reasonable pilot default.
